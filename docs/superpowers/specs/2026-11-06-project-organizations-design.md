## Approach options and recommendation

1. Extend existing private Paperclip with 120 explicitly mapped companies, one goal/project per company, real CEO/manager identities and bounded provider adapters. Native UAIN remains sole fund/task/review/reward authority. Recommended: directly supplies organizational roles without inventing a parallel workflow or ledger.

3. Put all work under one CEO/shared project team. Smaller provisioning change but fails the requested separate project leadership and organizational isolation; rejected.

Recommendation is a builder proposal, not a choice already approved by Rahul. Use existing JavaScript/Python/Go services and fixed provider fences; no new agent framework or new currency. ## Organization and authority

Each selected project receives a unique Paperclip company, CEO agent and Project Manager agent. Manager reports to CEO. Both have persistent role instructions, retained execution history and project-scoped access; real scheduled inference must be distinguishable from records. Assign licensed solver agents on demand and admit other normally licensed contributors through the same task path. Solvers are distinct from the paid central reviewer. Company count is 120; minimum leadership seats 240; workers are scheduled, not 120 unrestricted always-running processes.

CEO preserves the Main KPI, strategy and blockers; manager decomposes approved milestones, proposes task prices, assigns work and submits milestone evidence. CEO/manager cannot approve plans, verify their own contributions or unlock money. Neither receives a personal transfer of project allowance. A dedicated manager native identity signs only allowed project commands through custody. CEO has no generic signing capability. Guardian authority remains solely in the existing custody service for admission/start/evaluator configuration.

UAIN Fund Manager defines exactly five verifiable sub-KPIs from each unchanged Main KPI and independently reviews plan adequacy in a distinct execution. Central task reviewers and milestone verifiers operate outside project teams. Separate executions/identities and conflict checks are required; external human/operator recruitment is not a launch prerequisite. Preserve any existing native restrictions and the production reproduction gate; do not replace scientific verification with another agent saying yes.

## Durable operating flow

Run each external/native mutation from a durable intent journal: stable operation ID, project, source digest, exact payload hash, expected authority/revision, signer, retained envelope and verified receipt. One signer-wide sequence lane prevents cross-project nonce conflicts. Unknown outcomes enter reconciliation and prohibit blind resend/re-sign. Deterministic Paperclip bindings are reconciled before retry; same name is not an ownership proof. Hold uncertain creations rather than inventing duplicates. Restart and overlapping worker protection must survive crashes.

Shared execution pool starts at one running model job and one signer lane, round-robin across organizations. Reuse stricter existing caps where applicable. Persist leases, attempts, usage reservations, cancellation, backoff and per-project workspaces; no cross-company credentials/evidence. Workspaces have fixed tool permissions and no custody key access. Domain-specific executors/verifiers must qualify before those domains run. Medical or biological goals do not authorize patient operations, interventions or invented experimental evidence. A project with no valid automated task remains blocked, with exact evidence needs.

## Builder-review resolutions — 6 November

A fresh reviewer identified five implementation gaps; all are resolved here as proposed implementation choices rather than new product policy.

1. **Evidence classes:** first release supports (a) isolated source-code before/after reproduction with the existing protected attestation, (b) finite mathematical witnesses checked by an independently maintained deterministic verifier, and (c) reproducible analysis of pinned public datasets with a fixed, separately reviewed analysis driver and independent rerun. Each task pins its evidence class, input hashes, verification driver/hash and exact success tests before work. Trusted retrieval permits only prequalified primary-source HTTPS hosts, rejects redirects to unapproved hosts/private addresses and pins exact bytes/version; model-produced citations alone cannot establish prior art. Narrative literature notes remain unpaid preparation. Wet-lab, clinical efficacy, patient counts and unsupported evidence classes stay `verification_adapter_required`; no invented patient data or treatment actions. Verifier success proves the particular task result, never the project's broad Main KPI automatically. Each adapter must generate a submission/author/criteria/evidence-bound protected attestation through a fixed driver selected by root-owned task policy; untrusted code never selects the verifier.
2. **Compute:** extract the existing project-manager cost journal into a single locked durable accounting module, preserving its current journal and prior usage. Leadership and solver calls share the same $2/call reservation, $5/day and $25 tracked-rollout ceiling where this provider budget applies. A new journal must not reset consumed allowance. Daily exhaustion pauses until the next UTC accounting day; total exhaustion stays held pending explicitly approved budget change. Provider receipts reconcile reservations; unknown cost remains reserved. Other reviewer/Fund Manager provider calls retain their stricter existing attempt/time caps and are reported separately. These limits may prevent initial inference for all120 within the existing rollout allowance; report that as a capacity dependency, not completed leadership.
3. **Native mapping:** proposed new native ID is `P-<catalogue ID>`, persisted in the reviewed manifest before signing. An existing exact binding may be reused only after proof validation; never infer ownership from a matching name. Existing guardian/creator opens the eligible native project and remains project lead. Each project's distinct active licensed manager is explicitly designated by `central_project_start` and joined to the project; CEO is a Paperclip strategy identity with no guardian key. Solvers enroll/license/join normally. UAIN appoints a separate licensed evaluator; the central reviewer remains the existing authority. Native prerequisite checks decide admission, not the org registry. No lead transfer is inferred. Conflict with an existing project is held for reconciliation.
4. **Signer policy:** a root-owned source-pinned fleet policy is separate from model reports and runtime registry. It lists exact selected source/native/company bindings, manager/evaluator keys, operation allowlists and reviewed task/plan bounds. Atomic compare-and-swap revisions authorize changes. Model output cannot add projects, raise amount bounds, replace evaluator or change signer roles. Pilot helpers remain exact-target and unchanged; fleet custody has a new separately qualified entrypoint.
5. **Acceptance:** `operational-readiness.json` covers all120 organizations, leadership runs, approved plan, reserved task and actual bounded execution. `reward-acceptance.json` separately records submission, independent verification, final native awards and account readback for each project. A fixture or another project's receipt cannot fill a row. Overall user request remains incomplete wherever either required report has an unmet row. Scientific achievements and later real KPI releases remain separately reported.
